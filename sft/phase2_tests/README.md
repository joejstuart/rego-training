# Phase 2: Generate Rego Tests

## Purpose

For each instruction from Phase 1, generate a Rego test file that exercises
the rule. Tests are written following the OPA Policy Testing guide
(`data/opa_policy_testing.md`).

## Input

- `phase1_instructions/output/instructions.jsonl` — instructions with mock data

## Output

- `phase2_tests/output/tasks/<task_id>/<package_name>_test.rego` — one test
  file per instruction

## Test requirements

Every test file **must** include:

1. **At least one positive case** — the rule does NOT fire on valid input.
   Uses `not <package>.deny` with valid mock data.

2. **At least one negative case** — the rule DOES fire on invalid input.
   Uses `count(<package>.deny) > 0` with mutated mock data (missing field,
   wrong value, etc.).

3. **Minimal mock data** — tests inject only the fields relevant to the rule
   via OPA's `with input as {...}` keyword. No 2,400-line attestations in
   test files.

## Test patterns (from OPA testing guide)

### Basic positive/negative:
```rego
package predicate_type_check_test

import data.predicate_type_check

test_valid_predicate_type if {
    not predicate_type_check.deny with input as {
        "predicateType": "https://slsa.dev/provenance/v0.2"
    }
}

test_invalid_predicate_type if {
    count(predicate_type_check.deny) > 0 with input as {
        "predicateType": "https://example.com/unknown"
    }
}
```

### Using `with` for data mocking:
```rego
test_with_custom_allowed_types if {
    not predicate_type_check.deny
        with input as {"predicateType": "https://slsa.dev/provenance/v1.0"}
        with data.allowed_types as ["https://slsa.dev/provenance/v1.0"]
}
```

## Validation

After generating tests, validate syntax with:

```bash
for dir in phase2_tests/output/tasks/*/; do
    opa check "$dir" || echo "FAIL: $dir"
done
```

This catches syntax errors before Phase 3 tries to write rules.

## Running

```bash
cd sft/
python phase2_tests/generate_tests.py
```

## Results

| Tier | Count | Description |
|------|-------|-------------|
| 1    | 38    | Field-level (single value / presence checks) |
| 2    | 12    | Pattern-level (all-elements-must-satisfy checks) |
| 3    | 10    | Composite / semantic (cross-field logic) |

All 60 files pass `opa check` syntax validation.

### Mock data strategy by tier

- **Tier 1:** `mock_data` from Phase 1 is the *valid* case.  Negative mock is
  generated by mutating the target field (wrong value, missing key, bad format).
- **Tier 2:** `mock_data` contains arrays with mixed valid/invalid elements.
  Positive mock keeps only the first (valid) element; negative mock uses the
  full array as-is.
- **Tier 3:** Hand-crafted positive/negative mocks per instruction, fixing or
  breaking the specific semantic relationship being tested.
